# Open questions

Things this project knows it does not know, or has deliberately left for later. Each should
become a GitHub issue once the repository has a GitHub home. Until then this list is the tracker.

| Question | Why it is open | What would settle it |
| --- | --- | --- |
| What does a processor do when two clients register the same IP-ID? | The system this was developed on left conflicting notes: one observation that claiming a slot displaced nothing, and a later plan that assumed a deliberate collision would make the processor end the existing session. Neither was tested on purpose. See [ip-id-conflicts.md](../troubleshooting/ip-id-conflicts.md). | A controlled test on a slot no real panel uses, on more than one processor generation, with both clients logging. |
| Do analog and serial writes work? | The encodings come from [klenae/python-cipclient](https://github.com/klenae/python-cipclient). The development system's program accepted no analog write from a panel, so the bytes have never been seen to work. See [cip-wire-format.md](../protocol/cip-wire-format.md). | One report from a system whose program accepts analog or serial input from a panel. |
| Authenticated CIP | 3-series and 4-series processors can require a username and password. Nothing here has been tested against it. See [unsupported-systems.md](../troubleshooting/unsupported-systems.md). | Access to such a processor, and a capture of a real panel's handshake with it. |
| Encrypted CIP on real hardware | CIP over TLS is implemented ([ADR 0011](../adr/0011-cip-over-tls-with-a-pinned-certificate.md)) but tested only against the fake processor. Which TLS versions processors offer, whether the older-encryption setting (TLS 1.0 and 1.1) is ever needed in practice, whether Home Assistant's own Python builds still include those versions, and whether processors all greet a TLS client the way they greet a plain one, is unknown. | Someone with a TLS-enabled processor running `crestron-controller listen --tls`. |
| Joins in EXTENDED_DATA frames | The client reads digital, analog and serial joins from type `12` frames, and every record in a frame, following [rellis-erigon/Crestron-CIP-HA](https://github.com/rellis-erigon/Crestron-CIP-HA), which recorded a DMPS doing this. The development system's processors have only been seen to send serials this way, so the new paths are tested against fixtures only. The client decodes serial text as UTF-16 when bit `04` of the format byte is set, also following rellis; no processor has been seen sending that. See [cip-wire-format.md](../protocol/cip-wire-format.md). | A packet capture from a DMPS or 4-series processor, or a `crestron-controller listen` run against one that reports digital and analog joins correctly. |
| Do SmartObjects (lists) work? | The client reads SmartObject joins and join maps can name them with `smart_object:` ([ADR 0012](../adr/0012-smartobject-joins-are-their-own-namespace.md)), following the layout rellis-erigon/Crestron-CIP-HA captured. The development system's processors have not been seen sending any, so the whole path is tested against fixtures only. Also unknown: whether a list join the processor never mentioned should read as low, and whether lists ever nest. Choosing from a list (a `select`, or a `button` with `smart_object:`) uses an encoding no processor has been seen to accept ([ADR 0013](../adr/0013-writing-to-smartobjects.md)). See [reading and choosing from lists](../configuration/reading-lists.md). | A `crestron-controller listen` run, with debug logging, against a system whose panels have lists, compared with what the panel shows; for choosing, a test with someone present on an IP-ID no real panel uses. |
| Console login in the CLI | `crestron-controller ipids` and `crestron-controller console` answer a login prompt, but have only been run against consoles that ask for no password. | One run against an authenticated console. |
| Cursor-zone audio | A working pattern exists for audio zones selected through a per-slot cursor, but it was built and validated against one program only. See [cursor-zone-audio.md](../patterns/cursor-zone-audio.md) and [ADR 0009](../adr/0009-cursor-zone-audio-deferred.md). | A second program using the same pattern, so the generic version can be checked against two. |
| Panel project formats other than TSW x52 | `panel parse` now reads x60 and x70 `.ch5z` projects, experimentally. That reader was built from Crestron's npm packages and public sample projects on GitHub, and has never been run on a project taken from a real house or checked against a real processor. `panel fetch` is still x52-only, and whether an x60 or x70 panel hands over its project at all is untried. Older panel formats are still not read. See [x60 and x70 panels](../inventory/panel-project-files.md#x60-and-x70-panels-html5-projects) and [ADR 0014](../adr/0014-reading-html5-panel-projects.md). | A real x60 or x70 project, and a report comparing the draft `panel parse` makes from it with what `crestron-controller watch` shows; separately, a tested way to fetch the project from such a panel. |
| Has this run in a live Home Assistant? | The integration is tested in the Home Assistant test harness against a fake processor. Against one real processor (an AADS), `crestron-controller ipids` parsed the real IP table, `crestron-controller listen` registered and recorded the menu dump, and the integration's hub ran listen-only, refused the entry press, and sent no data frame beyond the update request. The integration has not been installed on a live Home Assistant instance. | Installing it on a live instance, listen-only first. |
| What does ONLINE mean for a gateway IP-ID? | On one processor, touch panel slots listed as `Gway` at 127.0.0.1 read ONLINE with their panel unplugged, and one slot's status changed between two reads minutes apart with nothing touched. | Watching the status across a panel being unplugged and plugged back in, with timestamps. |
